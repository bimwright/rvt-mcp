# Controlled failures and Revit Issues

This guide describes **unreleased development behavior**. It is not a published release or a completed native acceptance report. Candidate checks on Revit 2022, 2024 and 2027 are pending; Revit 2025/.NET 8 live acceptance has not run. Build coverage alone does not establish native behavior on every supported year.

## What changes

During an MCP edit, an unapproved Revit **Warning now requests rollback**, as do Error, DocumentCorruption and incomplete failure capture. Earlier versions of the shared helper deleted warnings and continued. The helper and native failure event now use the same policy so warnings are recorded before their state changes. Outside an MCP operation, normal Revit user actions retain their native behavior.

Warnings observed while natively opening or upgrading an existing model are recorded as opening context rather than attributed to a new agent edit. That exception does not accept Error, Corruption or uncertain capture: cancellation is attempted where the API permits, and the response reports the actual opening outcome.

A failure response includes `_failure`: the operation and incident IDs, model scope, action, mutation outcome, gate state, persistence state and bounded captured messages. `_operation` describes execution that is pending, interrupted or completed later. Read these fields even when custom code returned its own success value. `nextStep` says what the agent can do next: read the incident, survey with read tools and revise the plan; decisions stay with the user in Revit. Warnings that already existed in the model are recorded once as a baseline incident (`_operation.baselineIncidentId`) and are not reported as a failure of the call. A warning accepted by a user is still a warning and does not certify design quality.

The receipt's `modelScopeKey` identifies an explicit blocked model or the single model of its captured incidents. Typed `open_model` uses the claimed target, including background opens and refusals by the native pre-open guard before the target document exists; it does not fall back to the previously active document. If several models have incidents and there is no single explicit failure target, the key is null: query by `operationId` or `incidentIds` instead.

Rollback applies to the current supported transaction. A policy stop also prevents subsequent supported commits in the same call. `batch_execute` stops and rolls back its outer group even with `continueOnError=true`. Arbitrary code that already committed an earlier transaction can leave changes behind; such an outcome can be `partial` or `unknown`. External side effects are not undone by Revit rollback.

## Model gates and local records

A complete Revit rollback leaves the model unchanged: its incident stays open for the user, the model stays writable, and only the same request is refused (`REVIT_REQUEST_REPEATED`) until the user decides. A tool error that changed nothing (invalid arguments, code that did not compile or threw before committing) is returned to the agent without an incident. An uncertain operation outcome, incomplete capture or storage/identity failure blocks further MCP writes for the affected model (`REVIT_MODEL_BLOCKED`). Supported reads remain available when Revit's UI thread is free. Switching clients or restarting the gateway does not clear the gate. Durable saved-model state is retained across Revit restart; an unsaved or unresolved document may have only a live-session identity.

The failure ledger lives locally at `%LOCALAPPDATA%\Bimwright\rvt-mcp\failures\ledger.db`. It is separate from change history: disabling call logs or `_history` recording does not disable failure handling or erase rollback incidents. The add-in writes the ledger, so Issues remains usable when the gateway is stopped. If the ledger file is missing, a query creates a new empty database and reads that. An existing file is never replaced; **Reset** in Issues empties it after taking a backup (see below).

Rules start empty and apply to one model scope. A proven rename of the same physical file can retain its scope; a copy or Save As does not automatically inherit rules or grants. History-continuation choices do not grant failure-policy continuity. Missing records, an empty query result or an unrecognized identity are not proof that a model is safe.

Captured context is bounded. Raw code, credentials and full argument bodies are not failure-ledger content by default. Read `complete`, omitted counts, coverage and persistence fields. If durable storage fails, the add-in retains available in-memory blocking state and attempts a local recovery record. If neither store can be written, it reports that durability is unavailable; it cannot promise recovery across restart on an unwritable volume. Keep the records when troubleshooting rather than deleting the ledger to clear a gate; use **Reset** in Issues when you want to start over, because it keeps a backup.

## Handle an issue in Revit

Open **History → Issues** from the Revit ribbon or History window. Select the correct model and incident, inspect the outcome, captured elements and any incomplete evidence, then choose an action. The reason is optional: the input shows a hint while empty, and a blank or whitespace-only reason is recorded as `No reason provided`. Model-review confirmations and acceptance constraints still apply.

| Action | Effect |
| --- | --- |
| **Rework** | Records that the attempt will be reworked. It does not execute the revised operation. |
| **Abandon** | Closes the attempted action after review. It does not undo earlier commits, delete elements, save or discard the model. Partial or unknown outcomes require explicit confirmation that the model was checked. |
| **Accept once** | Grants one matching new attempt for supported, fully captured warnings or an exact supported dialog. It does not recommit a rolled-back transaction or retry the old call. |
| **Create rule** | Records a model-specific rule with the displayed definition, Revit year, context, count and existing-element constraints. Every observed failure must match. |
| **Revoke rule** | Disables a selected rule for future attempts. It does not undo previous changes. |
| **Allow native action once** | When available for a blocked native operation, authorizes only the displayed action, file/options and request context. It does not execute it. |

One-use grants expire after five minutes, are bound to the intended request and document revision, and can be invalidated by document changes, Undo, activation, reopening or Save As. New warning codes, unapproved existing elements, larger counts, incomplete capture, Error or Corruption cannot be accepted by a warning rule. A failed decision save preserves the previous gate/rule state.

**Reset** (next to **Refresh**) starts the ledger over. It first shows how many issues and open issues, in how many models, will leave the list, and how many blocked models it will unblock for MCP writes. After you confirm, it copies the whole ledger to `failures\backups\ledger-<yyyyMMdd-HHmmss>.db` (local time; `-2`, `-3`… if that name exists), then empties every table, rules and grants included, in the same write lock. The Revit models do not change. Reset is refused while an MCP operation is running or while unrecovered records wait in `failures\pending` (restart Revit to recover them first). If it fails, the ledger is unchanged. Open models are written to the empty ledger again the next time Revit is idle or a call starts. To inspect old records, open the backup read-only.

These decisions belong to the person using Revit. There is no public MCP approval, resolve, rule-edit or `approved=true` tool. Recording a change-history reason or telling an agent that an issue is accepted does not create a Revit Issues decision. The local decision record identifies the Windows/Revit user and UI channel; it is not a digital signature or isolation from arbitrary code running in the same process.

## Query without waiting for Revit's UI

These tools are in `meta` and remain exposed when the selected surface is read-only or send-code/history recording is disabled. They do not dispatch an ExternalEvent, retry a request or change the model, so they can answer while a native modal dialog is still open.

| Tool | Parameters |
| --- | --- |
| `revit_get_failure_records` | Supply an issued `modelScopeKey`, `incidentId` or `operationId`. Optional: `state`, `elementId`, ISO date/time `from` and `until`, `limit` (1–100, default 50), returned `cursor`, and `includeDetails` (default false). Follow `nextCursor` for further pages. |
| `revit_get_operation_status` | Required `operationId`. Optional `waitSeconds` (0–90, default 0): while the operation is unfinished (`waiting_for_user`, `timed_out_running`, `running`, `queued`), wait on the server, without holding Revit, and return as soon as it finishes; otherwise return with `stillWaiting=true`. A wait adds `waitedSeconds`. Returns available execution/outcome information, incident IDs and bounded final receipts. `available=false` means no durable status is available, not that the operation failed to run. |
| `revit_lookup_message` | Required `code`: a dialog code from `_operation.dialog` or `blockedBy.dialog`, or a failure GUID (`failureDefinitionId`). Returns the catalogue entry of the bound Revit year: a dialog's title, template text and buttons, or a failure's severity, description and resolutions. |

The local ledger keeps receipts, never a command's own result. `revit_get_operation_status` adds `finalResult.data` only while the gateway session that sent the call still holds it. That session also supplies `finalResult._userDialogs` (up to 8 KB), including when the operation has a ledger record; these reports remain in memory only. Read commands have no ledger record; for a read that returned a pending receipt, the status comes from that gateway session (`source: gateway_session`) and is lost when the server restarts. A result larger than 8 KB is omitted with its size; for a read, the reason suggests re-running it with a narrower request.

`revit_lookup_message` reads `%LOCALAPPDATA%\Bimwright\rvt-mcp\catalog\revit-<year>.json`. The add-in writes this file shortly after Revit starts, from the Revit installed on that machine and in its UI language, and rewrites it when the Revit build or language changes. Nothing from Autodesk is packaged with rvt-mcp. Add-in dialogs, Windows dialogs and dialogs without a code are not in the catalogue.

Use identifiers from receipts; these queries do not guess a model from its title and do not accept a file path instead of an identifier. Summaries and captured details have size limits. Use details and paging without claiming omitted evidence was checked.

## Modal dialogs, busy hosts and late results

Revit failures use the failure APIs. The add-in does not press generic OK/Cancel buttons or override `Dialog_Revit_DocWarnDialog`. Without a matching rule for a supported exact dialog, Revit retains its native dialog for the user and the call can report `REVIT_OPERATION_REQUIRES_USER` with `waiting_for_user`. Other UI-dependent calls to that busy host return `REVIT_BUSY`; inspect Issues/status instead of queueing another model operation.

A dialog shown during an MCP call is information for the agent. The pending receipt carries `_operation.dialog`: `code` (Revit's dialog ID, which can be empty or `0`), `kind`, the live `text`, and from the catalogue the `title`, `buttons`, `commonButtons` and `defaultButton`, plus `inCatalog`. A call refused with `REVIT_BUSY` carries `_operation.blockedBy` with the waiting operation ID and the same dialog. In the final `_failure.groups`, a dialog says `answeredBy`: `rule` (with the `answer` an adapter gave, when every occurrence got the same one), `user`, or `mixed` with `answeredCount` when a rule closed some occurrences and the user the rest. Revit does not report which button the user chose. When an operation that returned a pending receipt finishes, the next structured response of any tool, including tools that do not call Revit, carries its outcome and bounded result once as `_previousOperation`, unless the agent already read the final status. It includes the `_userDialogs` that operation reported. A response with no room for it leaves it for the next one. A plain-text error (`Error: ...`) carries nothing; the outcome waits for the next structured response, and `revit_get_operation_status` reads it at any time. `revit_switch_target`, `revit_get_change_records`, `revit_resolve_history_identity` and `revit_accept_bake_suggestion` send their own call to Revit and pass on what that call received. While an operation waits for the user, its `nextStep` says to call `revit_get_operation_status` with `waitSeconds`, or to tell the user it is still waiting. `revit_show_message` reports its own dialog with `kind=agent_message` and records no incident.

Dialogs and failure messages the user meets outside MCP calls stay exactly as Revit shows them; the add-in answers nothing and removes no warning. It notes them in memory per model: during a manual open, under the model being opened; otherwise under the active model. The next MCP call whose active model matches reports them once as `_userDialogs`, with a note that they are already closed and nothing is waiting. Items keep the code, kind, text and title, but not the buttons. A dialog with no ID (empty or `0`) and no text is skipped. They create no incident, gate or ledger record and are lost when Revit closes.

Manual failures are grouped by definition code. `count` counts occurrences; `textIsSample=true` means the text is from the first captured occurrence. Each operation scans at most 5,000 failure IDs and reads text/severity for at most 20 definitions. Counts are `countKind=at_least` when some IDs could not be read or exceeded that cap; `unreadFailures` reports their number. The buffer keeps 20 items and pages reports within 6 KiB. `omittedItems` counts omitted occurrences; `omittedFailures` gives code/count details for up to 20 known omitted definitions, and `omittedFailureDetailsTruncated=true` means further code details did not fit the retained summary.

The current dialog adapters cover only the observed Unresolved References and Analytical Changed contexts for Revit 2022 and 2027. They require a decision or rule for the exact dialog, year, context and displayed button meaning. Other years and dialogs remain manual. Incompatible central-version dialogs and **Project Not Saved Recently** are manual-only; the add-in does not choose Save or Discard for the user. A delayed reminder associated with an earlier blocked save may be reported as correlated without claiming causation.

Caller timeout and native execution completion are different events. A timed-out or disconnected request can still finish in Revit. A call that runs past its timeout without a reported dialog returns `REVIT_OPERATION_TIMED_OUT` with `timed_out_running`; `REVIT_OPERATION_REQUIRES_USER` is kept for a dialog or policy that needs the user. A request Revit never started because it was busy returns `REVIT_REQUEST_NOT_STARTED` with `outcome: not_started`: nothing ran, and it may be sent again. Retain the issued operation ID, inspect the native UI, and query the local final outcome before planning any new action. `timed_out_running`, `interrupted_unknown`, `partial`, incomplete capture or an unavailable record must never trigger an unchanged automatic retry. A completed result and actual model readback establish what happened; a responsive window alone does not.

Use a matching gateway and add-in build, and restart Revit after an add-in update. Non-read dispatch requires the controlled-failure capability handshake; `PAIRING_REQUIRED` means update the pair together. Tool discovery and an ordinary read do not prove the mutation policy ran.

## Native operation and API limits

Supported Open, Save, Save As and Synchronize pre-events check the live native context and any required one-use UI grant. A denied Sync is reported as cancelled even if the native API returns normally. If an event cannot be cancelled or its identity/options cannot be verified, the result reports enforcement unavailable or an unknown outcome; it does not claim a successful block.

A modified document's Closing event does not expose whether the caller intended save-on-close or discard. Controlled calls therefore require the user to close that document through Revit instead of guessing that choice. Application shutdown and user actions outside the MCP scope retain native handling. Save As, central upgrades, save-on-close, delayed reminders and storage-failure recovery still need their own native acceptance evidence; do not infer those guarantees from a successful build or a simple warning rollback.

`send_code` and custom baked implementations run arbitrary C# in Revit. Controlled failures are not a sandbox: another preprocessor can remove evidence before the supported adapters see it, and external side effects or arbitrary document operations may escape observation. Coverage is explicitly `dynamic_code_unverified` or `incomplete` where appropriate. Absence of captured failures never means complete design validation. See [send-code failure handling](send-code.md) and [change tracking](change-tracking.md) for the separate transaction and history boundaries.
